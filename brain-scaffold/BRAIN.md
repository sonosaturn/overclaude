# BRAIN — knowledge base schema

> This file is the **schema** of the second brain: it defines the structure, conventions and
> workflows the LLM must follow to build and maintain the wiki.
> Reference pattern: Karpathy's "LLM-maintained wiki"
> (raw sources → LLM-generated wiki → schema). The good part of AutoBrain
> (Obsidian vault + document ingest), **without** Jarvis/voice/webapp.

## Principle
The LLM does not get bored: it does the tedious work of summarising, cross-referencing and
maintenance. The human curates and asks. Answers are not fished out of the raw documents every
time: you build and maintain a **structured wiki** that sits between the user and the sources.

## Three levels
1. **`sources/`** — raw, immutable documents (PDF, md, converted txt). Never modified.
2. **`wiki/`** — markdown pages generated by the LLM: summaries, entity pages, `[[wikilink]]` cross-references.
3. **`BRAIN.md`** (this file) — the schema: structure rules and workflows.

Mandatory navigation files:
- **`index.md`** — catalogue of every wiki page by category.
- **`log.md`** — chronological record of ingests and changes.

## Wiki page conventions
Every page in `wiki/` has frontmatter:
```yaml
---
title: <Readable title>
aliases: [<synonyms for Obsidian>]
tags: [<category>, <topic>]
sources: [<file in sources/ or URL it derives from>]
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```
- File name: `kebab-case.md`, descriptive.
- Link related entities with `[[page-name]]` (this builds the Obsidian graph).
- A `[[link]]` to a page that does not exist yet is fine: it flags a page to write.
- Always cite the source: `(fonte: sources/<file>)` or a URL.
- One page = one concept/entity. No walls of text: summary + sections + links.

## Workflows

### INGEST (adding a source)
1. Convert the source to markdown with **markitdown** if it is not already:
   `markitdown <file> -o sources/<name>.md` (PDF, DOCX, PPTX, XLSX, HTML, audio…).
   Sources already in markdown are copied into `sources/` as they are.
2. Read the source, write a summary and **update/create** the relevant wiki pages
   (typically 5-15 files touched per source), with cross-references.
3. Update `index.md` (new pages) and `log.md` (an ingest line with the date).
4. One source at a time: incremental and clean beats bulk.

### QUERY (asking)
1. Search the wiki pages (`rg` over `wiki/`, or the Obsidian graph).
2. Synthesise the answer **with citations** to the pages/sources.
3. If the exploration produces new value, **file it** as a new wiki page.

### LINT (periodic maintenance)
Health check of the wiki:
- contradictions and stale statements;
- orphan pages (no incoming links);
- missing cross-references;
- `index.md` aligned with the real files in `wiki/`.
Record the outcome in `log.md`.

## Graph (optional)
`~/brain/bin/graphify-run.sh .` from the root generates a queryable graph in `graphify-out/`
(git-ignored) — an overview of entities and relationships.
The wrapper does **automatic fallback** across the Gemini models (`GRAPHIFY_GEMINI_MODELS` in
`~/.config/brain.env`) when one runs out of quota or is overloaded.

## Language
Content in the user's language unless the source dictates otherwise. Technical terms in
English when that is the standard form.

## Semantic recall (embeddings)
`bin/brain-embed --full` (a one-off backfill) indexes conversations/wiki/sources into ChromaDB
(`.chroma_db/`, gitignored) with Gemini embeddings. After that every commit updates only the
changed files (post-commit hook → `brain-embed --changed`). Query: `bin/brain-recall "..."`.
Dependencies resolved by `uv` (PEP723 inline in the scripts). Key in `~/.config/brain.env`.
